## Established path

The building tool's returned plate enumeration assigns Opening=2 and Hatch=3. After rebuilding buoyancy, `server_scene.vehicle._rebuild_buoyancy` calls the hatch manager to rebuild registration. `rebuild_vehicle_hatches` registers the two classes separately by plate type; both records contain vehicle, plate ID, area, normal, simplified vertices, and matched partner.

`_get_plate_node_positions_simplified` uses plate nodes, face-support offsets, and native node positions. Consecutive edges in the same direction are not all retained as separate corners. Comparing original `plates[].nodes` array lengths or the two component/vehicle origins alone is therefore insufficient.

Core conditions in `_check_hatch_opening_match`:

1. Both simplified node lists are nonempty and have equal counts.
2. Absolute area difference is **≤0.001** in the native area return value; this checkpoint does not presume conversion to m².
3. Normals transformed by their vehicles' world rotations have dot product **≤−0.99**, requiring nearly opposite directions.
4. Nodes are compared through each vehicle's complete world transform. The nearest initial node passing the distance test is found, then both forward and reverse cyclic correspondences are checked. Either complete cycle may succeed.
5. `_test_node_match` requires squared distance **strictly less than** `g_node_match_threshold_sq`. The initial threshold is **0.02**, squared in a separate constructor; equality fails. This is a native world-coordinate quantity in this path. No modified-geometry experiment was performed.

The predicate reads area, normals, vertices, and vehicle transforms without querying latch engagement. This establishes that no direct latch condition was found in this sealing-match predicate. It does not establish that latches never affect any door: holding physical alignment may indirectly affect matching.

The manager's `tick` compares unmatched hatches with unmatched openings. A match links both records and calls `vehicle_buoyancy.set_is_plate_opening_sealed(..., true)`. A paired object that ceases to match causes a false call and clears the relationship. This supports one-to-one matching and loss of sealing as alignment changes. Candidate choice depends on traversal order; overlapping candidates and exact tick scheduling have not been runtime-tested.

`set_is_plate_opening_sealed` writes buoyancy-plate byte **+0xc2** by plate ID. The opening-flow branch in `vehicle_buoyancy._calculate_forces` reads the same byte and requires **0**. Subsequent water-volume change uses covered area/water level, `g_opening_flow_rate`, and `g_server_delta_time`, with clamping. This connects matching to the actual water-flow path, beyond a suggestive symbol name.

## What this answers and leaves open

`static`: Hatch shape, corresponding nodes, area, orientation, and world position enter the sealing predicate. Geometric mismatch clears an existing pair and its seal flag. The predicate is not simply a latch-state check.

`inference`: The code supports an Opening being a buoyancy opening that a matching Hatch can seal. It does not support claiming every Opening unconditionally blocks water. Trace `vehicle_buoyancy.create` and default plate construction further before treating these partial paths as proof covering every initial state or exceptional geometry.

`unknown`: Player passage through each Opening geometry, frame collision, Hatch solid collision, and actual flooding rate/visible water level after opening. `vehicle_plate_util.add_static_geometry` is confirmed to dispatch opening/window/hatch/solid interior geometry by type before generating outer edges. That does not yet establish the collision-builder/player-capsule path; a rendered hole is not passage acceptance.

`unknown`: Indirect latch effects on sustained sealing, motion jitter, server/client behavior, seal restoration after saving/loading, complex nonconvex/simplified boundaries, and multiple candidates. No game experiments were performed.
